01

What I learned building an opinionated and minimal coding agent

Mario Zechner · Design overview

The best orientation to Pi's design. It covers the multi-provider model layer, event streaming, the four-tool surface, the small system prompt, and the features Pi deliberately leaves out. Read this first so the implementation details have an argument behind them.

02

Build Pi from a complete offline trace

Hands-on course · Chinese · TypeScript

A course that rebuilds a small Pi-like harness from a deterministic trace. It covers events, canonical messages, an agent loop, session trees, compaction, extensions, and evaluation. The checkpoint machinery is optional. The useful part is the sequence of mechanisms and failure cases.

03

Read the source and official documentation

Pi repository and current docs

Use the repository after the overview and course have given you a map. Focus on the model stream, agent loop, session manager, compaction, and extension types. Follow one execution path instead of touring every package.

Understand the state layer

04

Session file format

Official Pi documentation

Pi stores sessions as append-only JSONL entries linked by id and parentId. This explains how the active branch is rebuilt, how compaction entries act as checkpoints, and how branch summaries preserve useful state when navigating the tree.

05

Compaction and branch summarisation

Official Pi documentation

Focus on the cut-point rules, retained recent context, structured summaries, and cumulative file tracking. Compaction changes the context projection without deleting the underlying session history.

06

Extensions

Official Pi documentation

Extensions are Pi's main escape hatch. They can observe lifecycle events, register tools and commands, intercept tool calls, and change context or model behaviour without expanding the core agent. Read this after the loop and session model are clear.

Examine the tool-interface argument

07

What if you do not need MCP at all?

Mario Zechner · Design argument

The argument is not simply “CLI good, MCP bad.” It is about paying context cost only when a tool is needed: small command-line programs, documentation read on demand, and fewer schemas injected into every model request.

08

MCP vs CLI: benchmarking tools for coding agents

Mario Zechner · Benchmark

The empirical companion to the design argument. Use it to separate the effect of protocol choice from tool descriptions, ergonomics, model familiarity, and benchmark design.

09

Prompts are code, files are state

Mario Zechner · Workflow essay

The broader philosophy behind Pi: prompts express behaviour, plain files preserve inspectable state, and the harness should make both easy to read and change.

How to use this path

Do not read all nine links passively. For each mechanism:

  1. Predict the state and ownership rules before reading the implementation.
  2. Trace one successful execution from input to terminal result.
  3. Introduce one failure, such as an unmatched tool result or a consumer waiting when a stream closes.
  4. Explain the invariant that catches it without referring to the test output.

The goal is not to reproduce Pi feature for feature. It is to understand which parts of an agent harness must remain observable, durable, and correct when the model, tools, or user interrupt the happy path.
