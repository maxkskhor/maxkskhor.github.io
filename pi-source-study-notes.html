Pi Agent Harness: Source Study Notes

Pi snapshot 063fb963c · Reviewed 28 July 2026

Pi's architecture places four package boundaries around an ordinary agent loop. The model proposes actions. The harness owns scheduling, validation, execution, persistence, context construction, and user intervention.

These notes focus on mechanisms that should survive routine refactors. The implementation references were checked against earendil-works/pi at 063fb963c on 2026-07-28.

The package map

pi-coding-agent
├── pi-agent-core
│   └── pi-ai
└── pi-tui

The tree shows package dependencies and ownership. At runtime, agent events flow upward through the coding product and into TUI rendering.

Package Main responsibility
pi-ai Common model types, provider adapters, normalized streaming
pi-agent-core Generic loop, abstract tools, events, steering, cancellation
pi-coding-agent Concrete coding product, sessions, compaction, extensions, prompts
pi-tui Terminal input, layout, components, differential rendering

Provider adapters contain wire formats. The session layer owns durable product semantics. The terminal renders product events. Dependencies point from the coding product toward the generic loop and model packages.

The CLI is assembled from a small model layer, a reusable agent loop, and a product layer.

Reading a deterministic trace

A fixture is fixed test data. A scripted model response and a known tool result remove provider and environment variability, allowing a test to examine the harness sequence itself.

One complete tool trace contains different kinds of evidence:

user message
assistant tool call     model proposed an action
tool result             harness observed an environment outcome
assistant final         model continued from that observation

The tool call records intent and arguments. The result records the outcome paired by call id. A missing result leaves the proposed action without an observed outcome; it does not prove a particular failure such as "file read failed."

Trace events can also record ownership and progress stages. A schema may store both owner and type even when one can usually be derived from the other. That redundancy makes each event self-describing and allows validation to reject impossible pairs. A smaller production protocol could store only the event type and derive the owner.

Tests become useful once the invariant is explicit. For example, a fixture test can prove that every completed tool call receives one paired result and that a terminal assistant message follows it. Running the same test without knowing that invariant only proves that the current fixture matched the current code.

One history, several projections

Pi represents a conversation at several layers.

append-only SessionEntry[]
        ↓ choose active root-to-leaf path
SessionContext { messages, model, thinkingLevel }
        ↓ optional request-time transform
AgentMessage[]
        ↓ convertToLlm()
model-compatible Message[]
        ↓ provider adapter
provider request

Each representation answers a different question:

  • Durable session: what happened and what application state was recorded?
  • Active branch: which causal path is selected?
  • Agent context: which application messages belong to this run?
  • Model context: which messages can the model consume?
  • Provider request: how does one API encode those messages?

A fact can affect a request without becoming text. A stored model change restores control configuration. An excluded command execution can remain durable and visible in the UI while projecting to nothing for the model.

Stored fact Agent message Model message Other effect
Ordinary message Yes Yes Conversation history
Excluded command execution Yes No Still recoverable and renderable
Branch summary Yes Yes, translated Carries selected abandoned-branch knowledge
Compaction entry Yes, as summary Yes, translated Replaces an old prefix in context
Model change No No Restores provider and model selection
Thinking-level change No No Restores reasoning configuration
Extension custom entry No No Restores extension-owned state
Extension custom_message Yes Yes, translated Adds application-produced context

The durable record is the source of truth. Model context is a disposable projection.

"Canonical transcript" therefore needs qualification. The durable session is canonical for product history. The active AgentMessage[] is canonical for one selected branch and run. The provider receives a later projection with a smaller role vocabulary and provider-specific encoding. The message array sent to an API is derived state rather than the complete session transcript.

Provider-neutral inside, provider-specific at the edge

Pi separates provider service, API protocol, and model identity. The generic loop works with common messages. It resolves an adapter from the model's API, and that adapter owns the provider-specific request and response shapes.

For the same logical tool call:

  • Anthropic uses a tool_use content block with object input.
  • OpenAI Chat Completions uses tool_calls with JSON-string function arguments.
  • Pi retains structured common arguments and a stable call id.

The resolver selects the adapter. The adapter performs the encoding. The canonical session keeps the same structured arguments when another provider is selected.

The call id is the cross-provider pairing fact. Field names can vary, but a tool result must still be associated with the exact proposed call.

How EventStream suspends and wakes a consumer

Pi's generic stream separates incremental events from a final typed result:

EventStream<Event, Result>

It keeps three pieces of state:

queue       events produced before a consumer asks for them
waiting     Promise resolver functions for suspended consumers
finalResultPromise one Promise for the canonical result

Producer-first execution is ordinary FIFO buffering. push(event) adds an event to queue; the async iterator later removes the oldest item.

Consumer-first execution uses a Promise as a suspension point:

const result = await new Promise<IteratorResult<T>>((resolve) => {
  waiting.push(resolve);
});

The Promise constructor gives Pi the resolve function. Pi stores that exact function in waiting. A later push(event) removes one resolver and calls it:

const waiter = waiting.shift();
waiter?.({ value: event, done: false });

Calling the resolver settles the old Promise. The suspended iterator resumes after await with the supplied { value, done } object. There is no polling thread and no periodic queue check.

end() closes async iteration and wakes waiting iterators with done: true. result() returns the final-result Promise. For assistant streams, a terminal done or error event extracts and resolves the canonical assistant message. One consumer can therefore render every event while another simply awaits the completed result.

[Symbol.asyncIterator]() is the JavaScript protocol that makes for await work. Pi returns an async iterator that drains buffered events, waits when the queue is empty, and exits after closure.

Streaming is progress plus one result

A stream has two outputs:

  1. events for observing progress;
  2. one authoritative final result.

Pi adapters turn native chunks into normalized events for text, thinking, and tool calls. A terminal done or error supplies the completed assistant message.

provider chunks
      ↓ adapter-owned reconstruction
normalized progress events
      +
one completed AssistantMessage

Consumers take the final response from the terminal event. The adapter also owns partial tool-argument buffers, stop reason, usage, provider metadata, and error state.

During streaming, the low-level loop maintains one logical assistant-message slot. Start adds the partial message, each update replaces that slot with the newest accumulated partial, and completion replaces it with the canonical result. Replacement matters because the context may be observed while the response is still arriving. Appending every partial would turn one assistant response into many transcript messages.

The loop's private currentContext.messages and the public agent state are different arrays. Public state exposes the in-progress response through streamingMessage; it appends the completed message to public messages at message_end. The coding product uses the same event as its persistence boundary.

An event's delta is the new fragment. Its partial is the complete message accumulated so far. Partial tool arguments can be displayed, but execution must wait for the completed call.

The adapter owns reconstruction because it can see provider metadata, usage, stop reason, partial JSON buffers, and error state. A consumer that merely joins text deltas cannot recover all of those fields reliably.

The loop after a tool call

The essential tool-using turn is:

request assistant response
        ↓
append completed AssistantMessage
        ↓
extract and process its tool-call batch
        ↓
append one ToolResultMessage per call
        ↓
request another assistant response

The next model request must see the assistant's tool-call message before the paired tool results. The model proposes calls; the loop decides whether and how they run.

Tool failures normally become paired results so the model can observe and repair them. Provider-stream errors and aborts end the run.

A subtle truncation guardrail

If an assistant response ends because of the length limit, Pi fails every tool call in that response without executing any of them. Best-effort parsing can make truncated arguments look valid, so schema validation alone cannot prove that the model finished expressing its intent.

Batch scheduling

Pi chooses one execution mode for the entire tool-call batch. A global sequential setting, or any selected tool marked sequential, makes the whole batch sequential. Otherwise calls may execute in parallel.

In parallel mode, execution-end events can arrive in completion order. The canonical tool-result messages still follow the original call order. Listeners may therefore observe call-2 finishing first while the transcript appends the result for call-1 first.

A tool can return AgentToolResult.terminate: true, and the after-tool hook can replace that field. After every call has finished, shouldTerminateToolBatch() aggregates the finalized results. Its batch-level boolean becomes executedToolBatch.terminate. Pi suppresses automatic tool-driven continuation only when every finalized result has terminate: true; queued steering can still cause another assistant request. Tool implementations and trusted hooks own the hint. The model controls which registered tool it proposes and which arguments it supplies.

The source variable hasMoreToolCalls acts as a continuation flag. Pi resets it to false for each completed assistant response and sets it to !executedToolBatch.terminate after processing a non-empty batch. The first iteration starts with the flag set to true so the loop requests an assistant response before any tool call exists.

prepareNextTurn?.() is an optional hook at the end of a turn. It can return a replacement context, model, or thinking level before the next iteration. The ?.() syntax means "call this function when it is defined"; an absent hook returns undefined and the existing configuration stays in place.

Intervention has timing semantics

Pi distinguishes several operations that are often collapsed into one message queue.

Mechanism Delivery point Effect
Steering Next decision point after the current response and tool batch Changes the active run's next model request
Follow-up When the inner tool and steering loop would otherwise stop Adds another model request in the same run
Next turn During a later external prompt Waits without triggering a request
Abort Immediately marks the shared signal Cooperatively asks active work to stop

The nested loop structure reflects the priorities:

inner loop: model responses, tool continuations, steering
outer loop: re-entry for follow-ups

Pi assigns drained follow-ups to the same pending-message variable used by the inner loop, then continues the outer loop:

pendingMessages = followUpMessages;
continue;

There is no second enqueue operation at this boundary. On re-entry, Pi emits message lifecycle events for those pending messages, appends them to the active context, and then requests another assistant response.

Steering changes the next model decision after current work settles. abort() handles cancellation by marking the shared signal. A tool stops promptly only if it observes that signal or passes it to a cancellable API.

waitForIdle() awaits the active run promise. It does not poll. The promise resolves after the final listeners settle and run-owned state is cleared.

Follow-up and next-turn delivery occur at different boundaries. A follow-up extends the same active run before agent_end. A next-turn custom message sits in _pendingNextTurnMessages until a later external prompt() arrives. The current implementation adds that new user message first, then injects the pending next-turn messages alongside it.

Events are direct awaited dispatch

Event Meaning
message_start One logical message begins
message_update The current assistant or tool work has new progress
message_end The logical message reached its canonical final form
tool_execution_start Pi started processing a proposed call
tool_execution_update A running tool emitted non-canonical progress
tool_execution_end The tool pipeline produced its final outcome
turn_end One assistant response and its tool work finished
agent_end The run will emit no further loop events

tool_execution_start does not prove that the tool body ran. Lookup, validation, or policy can still reject the call.

subscribe(callback) stores the callback in an in-memory set and returns an unsubscribe function that removes it. When the loop emits an event, it calls the registered callbacks directly and in registration order. An asynchronous callback returns a Promise, and Pi awaits that Promise before advancing the loop.

The event triggers the function call. The returned Promise only reports when the callback's asynchronous work has settled. Consequently, an agent_end listener can delay the moment at which waitForIdle() resolves even though agent_end is the final loop event.

Core subscribers are low-level observers. The coding product subscribes internally and translates core events into persistence, extensions, retries, compaction, RPC, and UI behaviour.

Tool calls cross a trust boundary

Model-generated tool names and arguments are untrusted proposals.

lookup tool
    ↓
optional tool-owned argument preparation
    ↓
clone, coerce, and validate against schema
    ↓
before-tool policy hook may block
    ↓
check AbortSignal
    ↓
execute and capture thrown errors
    ↓
after-tool hook may replace result fields
    ↓
paired ToolResultMessage

Unknown tools, invalid arguments, policy blocks, cancellation before execution, and thrown errors become paired error results.

tool_execution_start is emitted before lookup and validation. It records that Pi started processing the proposal. A later error event can therefore pair with it even when execute() was never entered. The exact sequence for invalid arguments is:

tool_execution_start
schema validation fails
tool_execution_end with isError: true
message_start for paired ToolResultMessage
message_end

Validation occurs before policy. The trusted hook receives the validated mutable object. Pi does not validate it again if trusted code mutates it. The precise guarantee is therefore: model arguments are validated before entering trusted hook code.

Calls to onUpdate() produce live events only. The value returned by the tool becomes the canonical result in model context. Late updates after the promise settles are ignored.

Pi waits for listeners attached to already-emitted updates before it emits the final tool_execution_end. The optional after-tool hook then has the last trusted opportunity to replace content, details, usage, error status, or the termination hint before Pi constructs the ToolResultMessage.

Append-only sessions form a tree

Each durable entry has an id, parent id, timestamp, and type. Appending attaches a new entry to the current leaf. Branching moves the leaf pointer to an older entry; it does not delete the abandoned future.

A
└── B
    ├── C
    │   └── D
    └── E
        └── F   selected leaf

The JSONL file contains physical append order. The active conversation is the root-to-leaf path reconstructed from parent pointers. With F selected above, the active branch is A-B-E-F; C-D remains durable.

A branch summary is a new entry attached at the branch point. It carries useful conclusions from an abandoned branch without reactivating its raw messages.

Branching selects another projection while every old entry remains durable.

Compaction is another append-only projection

Compaction reduces future model context without deleting history. A compaction entry stores a summary and firstKeptEntryId, the boundary where raw retained context begins.

If a durable path is:

A → B → C → D → E → K

and K summarizes A-C while keeping from D, future model context is:

K(summary), D, E

All entries remain in JSONL.

A tool result cannot begin the retained suffix because its originating assistant tool call would be missing. When the boundary splits a long user task, Pi summarizes the earlier part of that turn so the retained assistant and tool messages keep their task context.

Repeated compaction incorporates the previous summary and messages that have since aged out of the retained window. Only the newest projection enters model context; earlier summaries and raw messages remain recoverable.

Repeated summarization remains lossy. Append-only history preserves the raw evidence needed to inspect, regenerate, or branch from before an omission, but it cannot guarantee that every updated summary retains every earlier fact.

Pi triggers automatic compaction around:

model context window - reserved compaction tokens

The reserve leaves room for the summarization request and its response. A separate keepRecentTokens budget controls how much recent raw context Pi tries to preserve; it does not set the summary length.

Token accounting uses the latest valid provider-reported assistant usage as an anchor when available, then estimates messages appended after that point. With no valid usage record, Pi estimates the whole context conservatively from characters. The compaction decision happens at a completed-turn boundary, when terminal usage is available. A failed or aborted summary request leaves the existing session untouched because Pi appends the compaction entry only after a successful result.

Extensions keep the core small by moving power outward

An extension is trusted TypeScript loaded into the Pi process. Its factory can register tools, handlers, commands, shortcuts, renderers, providers, and other behaviour. Extensions are not sandboxed. Project trust controls whether local code loads; it does not isolate the code once loaded.

The coding product maps an extension tool-call handler into the generic before-tool hook. Product policy can therefore reach the loop while package dependencies keep pointing downward.

Extensions have three distinct data paths:

Path Durable Model-visible Typical use
Tool-result details Yes No, unless repeated in content State owned by one tool result
Plain custom entry Yes No Extension or UI state
custom_message Yes Yes, converted to user role Application-produced model context

Extension tool code produces tool-result details. Pi transports and persists them, while the model only proposes the registered call.

The model can request a registered extension tool, but the extension's execute() implementation constructs both returned fields:

content   text or media intended for the model and user
details   structured extension or UI state

Keeping branch-specific tool state in details attaches it to the exact call and result that produced it.

A plain custom entry records extension state that never enters model context, such as a session-specific panel preference or indexing-status card. Extensions can scan their own customType entries during replay and rebuild internal state.

After conversion, a custom message looks like a user-role message to the provider. Its distinct application representation still preserves provenance, custom rendering, structured details, and delivery semantics. Provider-visible provenance must be written into the message content.

The transformation is explicit:

JSONL entry:       type "custom_message"
runtime message:   role "custom"
provider message:  role "user"

customType, display, and details stop at the application boundary. The provider receives the converted content and timestamp. An extension should use a real user message when the content is meant to be recorded and rendered exactly as human input.

The custom message kind controls storage and model projection. deliverAs controls when that message enters the loop: steering, follow-up, or next-turn delivery.

Secrets belong in none of these session entries. Session JSONL is not a secret store.

Deliberate product boundaries

Pi's coding-agent README explicitly omits built-in MCP integration, subagents, permission popups, plan mode, todo management, and background bash. The project routes each need toward an existing operating-system tool, a plain file, or an extension.

Omitted core feature Pi's route Benefit Cost
Background bash manager tmux Shared live terminal, inspectable logs, no hidden process registry Requires tmux knowledge and manual lifecycle discipline
Permission popups Container or sandbox for isolation; extension for confirmations Security boundary can cover filesystem, process, network, and credentials Default local execution has the user's permissions
Built-in sandbox Container, VM, micro-VM, remote sandbox, or policy-controlled runtime Isolation is enforced below the harness Setup and workspace transfer become the user's responsibility
MCP client CLI programs with on-demand documentation, or an extension Small default tool surface and less schema context Weaker built-in discovery and structured interoperability
Subagent runtime Spawn separate Pi processes, often through tmux, or install an extension Core avoids choosing one orchestration and context-isolation model Packages can disagree on scheduling, state, and failure semantics
Plan mode and todos Markdown files or extensions Plans remain inspectable and editable with ordinary tools No standard workflow or UI across installations

These choices make the default product small and composable. They also move integration work onto the user. A team that needs centrally enforced policy, standardized approval UX, or one supported subagent protocol may prefer those facilities in the product core.

Background work through tmux

tmux is a terminal multiplexer and a small process supervisor. A named session continues running when no client is viewing it.

  • Attach enters an existing session and displays its panes.
  • Detach leaves the display while commands continue running.
  • capture-pane reads the same terminal output that a human sees.

Pi can issue ordinary shell commands such as:

tmux new-session -d -s project-dev 'npm run dev'
tmux capture-pane -p -t project-dev
tmux attach -t project-dev

The shell, tmux server, and operating system hold the process state. Pi keeps no parallel object saying that server 42 is alive. The user can attach to the same pane, read the same failure, type a diagnostic command, and detach again.

This approach works only when Pi and the human can reach the same tmux server. A Pi process inside an isolated container cannot see tmux sessions running on the host unless the environment has been arranged to share them. Session names, cleanup, port ownership, and process shutdown also remain operational concerns.

Security boundary and workflow policy

Pi runs with the permissions of the process that launched it. Project trust decides whether project-local settings, packages, resources, and extensions are loaded. Once loaded, an extension executes as trusted in-process code.

OS-level containment supplies the real isolation boundary:

  • restricted filesystem mounts limit which files can change;
  • omitted credentials remove access to external systems;
  • network policy limits destinations;
  • a separate low-privilege user reduces host access;
  • containers, VMs, micro-VMs, and policy sandboxes isolate the entire process.

An extension permission gate serves a different purpose. It can ask for confirmation, block command patterns, or apply organization-specific policy. Its decision still runs inside the same process and cannot replace filesystem, network, process, or credential isolation.

Small core, varied products

The extension system makes most omissions reversible. Pi ships examples for permission gates, sandboxed tool execution, plan mode, and subagents. The core therefore defines the loop and extension points while packages choose the workflow.

The resulting installations can differ substantially. Two Pi users may have different approval semantics, subagent protocols, plan formats, and MCP support. The small core gives individual users freedom and gives teams less standardization out of the box.

Design summary

  • The agent runtime uses ordinary nested async loops.
  • Provider conversion occurs at the model boundary.
  • Streaming progress and canonical results use separate channels.
  • Tool calls cross validation and policy gates before execution.
  • Durable history, active branch, model context, and provider requests are separate projections.
  • Branching and compaction preserve append-only evidence.
  • Steering, follow-up, next-turn delivery, and abort have explicit timing.
  • Trusted extensions carry product policy and optional workflows.
  • tmux and OS isolation handle process supervision and security outside the core harness.

The remaining source study covers the TUI boundary and a direct comparison with a harness that standardizes more of these product decisions.

TypeScript encountered while reading Pi

These syntax points explain the inspected mechanisms. Extension event overloads remain outside the current scope.

ESM imports use runtime filenames

Pi uses ECMAScript modules. A TypeScript source file may import "./events.js" while the file on disk is events.ts. TypeScript resolves the source during compilation, then emits JavaScript whose runtime import still points to events.js.

Optional calls

const messages = (await getSteeringMessages?.()) || [];

callback?.() calls callback when it is defined and produces undefined when it is absent. Pi then falls back to an empty array.

Discriminated unions and never

An event's literal type field narrows the union inside a switch. An exhaustive default can make a missing case a compile-time error:

default: {
  const unreachable: never = event;
  return unreachable;
}

If every variant was handled, event has narrowed to never. Adding a new variant without another case makes the assignment fail.

Standard protocol types

IteratorResult<T>, AsyncIterator<T>, Promise, and Symbol.asyncIterator come from JavaScript and TypeScript's standard libraries. A generic parameter such as T or Event is a local type variable chosen by the class author.

Object keys need quotes when they contain spaces, punctuation, or other syntax that prevents identifier notation. Keys such as type, value, and done work without quotes.

Exercises without solutions

1. Truncated batch with intervention

The model streams two valid-looking tool calls but the assistant response ends because of the length limit. While it streams, the user queues one steering message and one follow-up.

Trace which tools execute, which paired results are created, and when each queued message first becomes model-visible. Label every decision as model-owned or harness-owned.

2. Branch plus compaction

Start with a user message, assistant tool call, paired tool result, final assistant response, model change, and another completed turn. Branch before the model change, append a branch summary and a new user message, then compact while retaining only that new user message as raw context.

Reconstruct the durable tree, active path, next model context, restored model configuration, and every raw entry that remains recoverable.

3. Trusted hook mutation

A schema requires { path: string }. Valid model arguments pass validation, a trusted hook mutates path to a number, the tool emits progress, returns an error result, and later emits one stray progress update.

Trace the validations, the actual execution input, event sequence, canonical result, and which surprising behaviour belongs to trusted code rather than the model.

4. Extension state and delivery

Place three values correctly: branch-specific state returned by a tool, a durable UI preference the model must never see, and a notice the model should see only with the next external user prompt.

For each value, describe its JSONL representation, runtime message projection, provider-visible form, rendering behaviour, and delivery timing.

5. Provider-neutral replay

A session records a tool call while using Anthropic. The user branches, changes to an OpenAI-compatible model, and resumes from the same common call and result.

Identify what must remain provider-neutral, where the active path is rebuilt, where wire-format conversion occurs, and what would fail if provider-native tool blocks had been stored as the canonical session representation.
