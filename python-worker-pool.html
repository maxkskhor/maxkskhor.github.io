From blocking queue to worker pool

A worker pool is not mysterious infrastructure. It is a queue, a fixed group of consumers, a completion protocol, an error channel, and a lifecycle contract.

1. The worker system as a small machine

The smallest useful worker system has five responsibilities:

Submitaccept work
Queuebuffer and limit
Workersprocess concurrently
Lifecyclefinish and stop
  1. Intake: decide whether new work is accepted.
  2. Backpressure: decide what happens when work arrives faster than workers finish it.
  3. Execution: let a bounded number of workers process independent items.
  4. Completion: distinguish removing a job from actually finishing it.
  5. Shutdown: define when submissions stop, what happens to queued work, and how workers terminate.

The queue protects communication between producers and workers. It does not, by itself, answer whether the system is open, whether work succeeded, or when every worker should exit.

The main design skill is turning vague words like “done” and “shutdown” into observable state transitions.

2. Retrieving work is not completing work

A worker calling get() only claims an item. The job may still be running—or may fail. This is why queue.Queue maintains a separate unfinished-task count:

put(job)       → unfinished count + 1
get()          → queue item removed; count unchanged
task_done()    → unfinished count - 1
join()         → wait until unfinished count = 0

Suppose the queue physically becomes empty while two workers are still processing. queue.empty() may be true, but the batch is not complete. queue.join() waits for the stronger fact: every accepted item has a matching task_done().

job = jobs.get()
try:
    process(job)
finally:
    jobs.task_done()

The finally is not cosmetic. If processing raises and skips task_done(), the unfinished counter never reaches zero and another thread can remain blocked inside join() forever.

3. The worker loop

A long-lived worker repeatedly claims and processes items. On Python versions before 3.13, a common teaching pattern uses a unique sentinel object to mean “terminate this worker”:

STOP = object()

def worker():
    while True:
        item = jobs.get()
        try:
            if item is STOP:
                return
            process(item)
        finally:
            jobs.task_done()

Use a unique object and identity comparison so a normal input cannot accidentally equal the sentinel.

One sentinel stops one worker

A sentinel is an ordinary queue item. The first worker that retrieves it exits. With four workers, enqueue four sentinels if all four must terminate.

for _ in workers:
    jobs.put(STOP)

The sentinel also increments the unfinished-task count, so the worker must call task_done() for it. Otherwise a later queue.join() can hang.

A sentinel is a message inside the data stream. Closure is state on the queue itself. They can implement similar user-visible outcomes, but they are not the same abstraction.

4. Backpressure: bound the waiting work

If producers can enqueue without limit, the queue becomes an unbounded memory buffer. A bounded queue makes overload visible:

jobs = Queue(maxsize=capacity)
jobs.put(item)  # waits while full

Backpressure means slowing intake because downstream work cannot keep up. It is not automatically an error. The system must choose a policy:

Block

Wait for capacity. Simple and lossless, but may propagate latency upstream.

Timeout

Wait up to a limit, then surface overload to the caller.

Reject

Fail immediately when full. The caller decides whether to retry.

Drop

Discard selected work. Only valid when loss is explicitly acceptable.

A worker count limits simultaneous execution. Queue capacity limits accepted but not-yet-completed work. They control different resources.

5. Graceful shutdown is an ordering protocol

For a simple system where one coordinator submits all work and then shuts down, the safe sequence is:

1. stop producing normal jobs
2. wait for accepted jobs to finish: jobs.join()
3. enqueue one STOP sentinel per worker
4. wait for sentinel tasks: jobs.join()
5. join every worker thread
for item in inputs:
    jobs.put(item)

jobs.join()

for _ in workers:
    jobs.put(STOP)

jobs.join()

for thread in workers:
    thread.join()

This works under an important assumption: nobody submits normal work after the coordinator begins shutdown. If independent producers can race with shutdown, sentinels are not enough to define an atomic “closed for submission” boundary.

For that stronger contract, use the closeable condition-based queue from the previous guide, or Python 3.13+ Queue.shutdown(). Modern queue shutdown rejects future puts, wakes blocked producers, permits graceful draining, then makes gets fail once empty.

Graceful versus immediate

Graceful

Reject new work, finish accepted work, then stop workers.

Immediate

Stop waiting quickly and abandon some queued work under an explicit contract.

Immediate shutdown breaks the ordinary meaning of “join means everything was processed”. Treat it as a separate operation, not a faster implementation of graceful shutdown.

6. Why a stop Event is not enough

This loop looks plausible:

while not stop_requested.is_set():
    item = jobs.get()
    process(item)

But the worker cannot inspect the event while blocked indefinitely inside get(). Setting the event does not wake a queue waiter.

Three coherent alternatives are:

  1. Send sentinels through the queue.
  2. Use queue closure that wakes blocked operations.
  3. Use a finite get(timeout=...), catch Empty, then re-check the event.

The timeout approach introduces periodic wake-ups and shutdown latency. It is useful when work already has natural polling intervals, but a sentinel or closeable queue is usually cleaner for a pure worker pool.

7. Make worker failures visible

An uncaught exception ends a raw worker thread and is printed by Python, but Thread.join() does not re-raise it in the coordinator. The main flow can incorrectly continue as if the batch succeeded.

A small raw-thread design can catch and record failures:

try:
    process(item)
except Exception as exc:
    with error_lock:
        errors.append((item, exc))
finally:
    jobs.task_done()

Decide whether one failure should stop intake, allow independent jobs to continue, or trigger retries. “Catch every exception” is not a failure policy; it merely makes policy possible.

Completion guarantees need careful words

Inside one healthy process, a queue can arrange for each accepted object to be claimed once. That is not durable “exactly once” execution: the process can crash after an external side effect but before recording completion. Durable systems need idempotency, persistent state, or acknowledgement protocols beyond an in-memory thread pool.

8. ThreadPoolExecutor packages the common case

The high-level interface accepts callables and returns futures:

from concurrent.futures import ThreadPoolExecutor, as_completed

with ThreadPoolExecutor(max_workers=4) as executor:
    futures = [executor.submit(fetch, url) for url in urls]

    for future in as_completed(futures):
        result = future.result()

A Future is a handle to one eventual outcome. result() waits if needed, returns the value, or re-raises the worker exception in the caller. as_completed() yields futures in finishing order rather than submission order.

pending → running → finished with value
                  → finished with exception
        ↘ cancelled before running

Executor shutdown

shutdown(wait=True) stops new submissions and waits for pending work. With cancel_futures=True, tasks not yet started are cancelled; running tasks are not forcibly terminated.

Even shutdown(wait=False) does not make the Python process exit while pending executor work remains. Use the executor as a context manager for the ordinary drain-and-wait contract.

Pool starvation deadlock

If every worker is occupied by a task waiting on another future scheduled onto the same exhausted pool, no worker remains to run the dependency. Avoid making pool tasks synchronously wait for work that requires a free worker from that same pool.

9. Custom workers versus an executor

Custom queue + threads

Best for learning, explicit backpressure, unusual lifecycle rules, streaming consumers, or custom scheduling.

ThreadPoolExecutor

Best for submitting independent callables and collecting results or exceptions with minimal machinery.

The executor is not “more concurrent”. It is a higher-level contract over a worker pool. Reach for the simplest abstraction that directly represents the behavior required.

Base contract

  • Constructor validates positive integer worker count and capacity.
  • Workers start once and remain alive while waiting for work.
  • Every submitted item is processed exactly once within the healthy process.
  • The bounded queue applies backpressure to submit().
  • shutdown() waits for accepted jobs before stopping workers.
  • Every worker terminates; shutdown does not leave daemon threads behind.
  • The test does not assume a particular global completion order.

Tests to write before extensions

  1. Two workers process six distinct items.
  2. All output items appear exactly once, in any order.
  3. After shutdown, every worker reports is_alive() == False.
  4. The queue's unfinished-task count reaches zero, observed through a returning join().
  5. Capacity one still makes progress with multiple jobs.

The base contract intentionally assumes submissions finish before shutdown begins. Do not quietly add concurrent submit-versus-shutdown semantics. That is a separate extension requiring an atomic lifecycle boundary.

11. The async version has the same machine

asyncio.Queue has the same conceptual unfinished-task count, task_done(), and join(). The execution units are event-loop tasks rather than OS threads:

async def worker(queue):
    while True:
        item = await queue.get()
        try:
            if item is STOP:
                return
            await process(item)
        finally:
            queue.task_done()

Async queue methods do not take timeout parameters. Compose timeouts around awaitables, for example with asyncio.wait_for() or the modern timeout context manager.

Cancellation is injected at an await point. Cleanup still belongs in finally. If a task claimed a queue item before cancellation, it must preserve the completion invariant or explicitly requeue/abandon the item under a defined policy.

Do not use asyncio.Queue for communication between OS threads; it is designed for async tasks. Likewise, a blocking queue.Queue.get() inside the event-loop thread would freeze all coroutines on that loop.
